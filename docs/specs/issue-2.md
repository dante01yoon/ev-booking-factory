# 이슈 #2 — 내 예약 카드의 취소와 환불 예정액 안내

- 요청: 「예약 취소 기능을 넣어 주세요」 (`.factory/issue.json`, #2).
- 상태: 사람 검토용 스펙 초안. 아래 추천안은 미확정이며 구현 승인이 아니다.
- 작성 범위: 이 문서 한 파일. 코드·테스트·기존 정책 문서는 변경하지 않는다.

## 사용자 문제

예약을 확정한 운전자는 일정이 바뀌었을 때 내 예약에서 취소할 방법을 찾을 수 없고, 취소 전에 예약금이 얼마나 반환되는지 확인할 수 없다. 요청은 내 예약 카드에 취소 진입점을 제공하고 환불 예정액을 미리 안내하는 것이다.

관련 스토리는 US-07(사용자 취소), US-06(내 예약·결과 조회), US-03(소유자 권한·예약 제한 해제)이다. 기존 정책에 취소 규칙은 있지만 화면 연결이 빠져 있다. `src/preview/public/app.js`의 예약 카드는 체크인·노쇼 시연·충전소 보기만 제공하며, PRD 7과 `docs/browser-preview-validation.md`도 사용자 취소 화면이 미연결이라고 기록한다. `src/rules/refund.ts`에는 사용자 취소 계산·중복 효과 방지 함수가 있다. 함수의 존재를 취소 API·화면·외부 환불 완료 근거로 간주하지 않는다.

## 화면에서 바뀌는 것

다음은 T-21·T-23·T-24에 대응하는 제안 흐름이다. 구체적 화면 방식과 경합 처리는 아래 사람 결정 항목을 따른다.

1. 로그인한 운전자의 내 예약 카드에서 **예약 취소**로 진입한다. 결제 대기와 확정 예약을 구분하고, 이미 취소·노쇼·종료된 카드를 새 취소 대상으로 취급하지 않는다(AC-06-1, PRD 4.2.1). 타인의 예약 조작은 처리 경로에서도 거절한다(AC-03-4).
2. 취소 전에 충전소·충전기, 원래 시작·종료 시각, 서울 시연용 현재 시각, 예약금 3,000원과 **환불 예정액**을 표시한다(T-24, AC-07-1~3). 원래 시작까지 120분 이상은 3,000원, 30분 이상·120분 미만은 1,500원, 30분 미만·시작 후는 0원이다. 0원도 명시적으로 안내한다.
3. 취소 후 내 예약에서 **사용자 취소**와 환불 금액·처리 결과를 확인할 수 있게 한다. 예정액·환불 요청·성공 확인된 반환액을 구분하고, 외부 환불 성공 확인 없이 완료로 표시하지 않는다(T-18·T-24, AC-06-1~2·AC-07-4).
4. 취소된 예약은 진행 중 예약 1건 제한에서 제외한다(AC-03-3). 반복 클릭·반복 응답으로 추가 환불이나 대기자 중복 승계를 만들지 않는다(AC-07-4).

체크인 후 사용자 취소는 이용 종료와 구분해야 한다. 시작 후 사용자 취소 환불은 0원이며, 체크인한 예약의 이용 종료는 전액 반환이다(PRD 4.2, AC-07-3·AC-09-1). 종료 버튼 구현은 별도 T-27·T-29 범위다. 운영자 취소 화면은 T-41·T-42 범위이며 이번 사용자 취소와 합치지 않는다.

## 계산 예시

일반 예약의 원래 시작은 `2026-10-06 14:00:00`, 종료는 `15:00:00`, 결제된 예약금은 정수 3,000원이다. 아래 시각은 모두 서울 시연용 시계이며, 예약은 아직 취소·노쇼·종료되지 않은 상태를 전제로 한다.

| 취소 시각 | 원래 시작까지 남은 시간 | 환불 예정액 | 반환하지 않는 금액 | 근거 |
|---|---|---:|---:|---|
| 11:59:59 | 120분 1초 | 3,000원 | 0원 | AC-07-1 |
| 12:00:00 | 정확히 120분 | 3,000원 | 0원 | AC-07-1 |
| 12:00:01 | 119분 59초 | 1,500원 | 1,500원 | AC-07-2 |
| 13:29:59 | 30분 1초 | 1,500원 | 1,500원 | AC-07-2 |
| 13:30:00 | 정확히 30분 | 1,500원 | 1,500원 | AC-07-2 |
| 13:30:01 | 29분 59초 | 0원 | 3,000원 | AC-07-3 |
| 14:00:00 | 0분 | 0원 | 3,000원 | AC-07-3 |
| 14:05:00 | 시작 후 5분 | 0원 | 3,000원 | AC-07-3 |

승계 예약도 확정 시각이 아닌 **원래 시작 시각**을 기준으로 계산한다. 원래 시작 14:00, 승계 확정 14:20, 취소 14:21이면 환불은 0원이다(AC-07-5, T-22).

13:30에 취소하여 1,500원 환불을 성공 반영한 뒤 같은 요청·성공 결과가 반복되어도 누적 환불은 1,500원이다(AC-07-4). 미정인 실패 재시도·동시 이벤트 결과는 계산 예시로 확정하지 않는다.

## 완료 기준

이 공정은 스펙 작성까지다. 아래 기능 기준은 사람 결정과 선행 조건 확인 이후 구현·리뷰 공정에서 검증할 기준이다.

1. 자신의 유효 예약 카드에서 취소 진입과 확정 전 환불 예정액을 확인하고, 타인 조작은 거절한다(US-03·06·07, AC-03-4·AC-06-1~2, T-24).
2. 계산 예시의 모든 경계에서 정확한 정수 금액을 표시하고 동일한 순수 규칙을 처리 경로에서도 호출한다. 승계 취소는 원래 시작 기준을 유지한다(AC-07-1~3·AC-07-5, T-22).
3. 사용자 취소 사유, 진행 중 제한 해제, 실제 환불 상태를 반영한다. 환불 0원도 취소 결과로 표시하고 정상 이용 종료·운영자 취소·노쇼와 구분한다(AC-03-3·AC-06-1~2·AC-07-3, T-23·T-24).
4. 같은 취소·환불 성공 결과를 반복해도 금액·상태·승계 효과는 한 번만 반영된다(AC-07-4). 실패·경합·미리보기 금액 변경은 사람 답변으로 확정한 기준을 검증하며, 미정 상태에서 성공 경로를 만들어 통과시키지 않는다.
5. 대기자가 있는 통합 취소는 관련 C 결정과 T-32 이후 범위 완료를 확인한다. 이벤트 연결점만 구현한 결과를 자동 승계 완료로 보고하지 않는다.
6. 모바일 화면에서 전액·부분·무환불 미리보기와 취소 결과 증거를 남긴다. 규칙 테스트·모의 처리·브라우저·토스 테스트 실연결을 구분해 AC별 `PASS / FAIL / BLOCKED / NOT_RUN`을 기록한다(T-47·T-48). 실패 재현 테스트는 후속 재현 공정에서만 작성하고 기존 테스트는 수정하지 않는다.

이번 스펙 검증 상태: 문서·이슈·관련 코드의 정적 대조 `PASS`. 기능 테스트·모의 처리 실행·브라우저 검증·토스 테스트 실연결은 모두 `NOT_RUN`. 기존 검증 기록을 이번 실행 결과로 전용하지 않는다. 스펙 작성은 기능 수정 완료나 사람의 정책 결정 완료를 뜻하지 않는다.
